# Project review and implemented changes

The app is a Spring Boot 4.1 / Java 21 service with MySQL, JPA entities and a
static HTML/vanilla JavaScript interface. Tailwind styles are compiled from
`frontend/`; page structure is generated by `frontend/genpages.py`. H2 is used
only for tests. Authentication already existed, but several content endpoints
had not been connected to it.

## Findings addressed

| Finding | Change |
| --- | --- |
| Claim references exposed conversations and allowed replies without login. | Every read and action requires a stored participant account. |
| A client could choose `fromPoster` and impersonate the other party. | The authenticated participant determines the author and action permissions. |
| Claimant/reporter emails were client-controlled. | New posts and claims attach account IDs and take names/emails from the session. |
| All uploaded images were exposed through a static directory handler. | Public files are served individually; private photos use a permission-checked endpoint. |
| MIME labels alone were trusted for uploads. | Check image signatures and decode supported JDK formats; check WebP container metadata. |
| No security question protected chat. | Generated category prompts, editable questions, hashed answers and persistent account lockouts. |
| Existing private comment submission bypassed chat verification. | New private messages use verified claims; legacy private comments use account ownership checks. |
| Chat did not refresh incoming messages. | Five-second polling, draft preservation, duplicate-send guards and bounded scrolling. |
| Browser storage defined the dashboard and could misidentify the viewer. | Account queries define posts, incoming claims and viewer roles. |
| API helper discarded validation field details. | Preserve field errors for inline form feedback. |
| Login retained the session ID and accepted arbitrary redirect destinations. | Rotate the session ID and constrain redirects to this origin. |
| Published moderation key and demo credentials were enabled by default. | Both require explicit opt-in; administrators can be provisioned through bootstrap environment settings. |
| Seeding restored account roles/approvals and adopted guest content by email. | Preserve existing decisions and stop email-only adoption of private guest records. |
| Concurrent claim actions could overwrite item lifecycle state. | Serialize lifecycle mutations with an item database lock and refresh entities after acquiring it. |
| Report success promised email that does not exist. | Describe browser match alerts accurately. |

## Deployment and migration limits

- New reports, claims and chat require approved accounts. Browsing and public
  comments remain public. Configure the first administrator as documented in
  the README; approval alone does not verify ownership of a particular item.
- Existing accounts with published demo passwords are not deleted or reset by
  this change. Operators must rotate those credentials before deployment.
- Existing public photographs stay public. Upload identifying evidence using
  the private field; a secret visible in public content defeats its question.
- Unlinked legacy guest claims/posts require an operator to verify and attach
  the correct account. Existing linked claims without verification require
  poster review before chat messages can be sent.
- Question generation uses deterministic category templates, not an external
  AI service or image recognition. Posters must supply a real private answer.
- WebP has no JDK decoder, so its validation checks the signature, declared
  file length and chunk type; JPEG/PNG/GIF additionally use ImageIO decoding.
- Private files persist under the same uploads volume as public files. The
  current Render free-tier configuration still needs durable file storage.
- Sessions and notification state are not distributed. Horizontal deployment
  would require shared session storage; alerts have no email/push delivery.
- Login attempts and public comments do not yet have abuse throttling. The
  new five-failure throttle specifically protects security-question answers.

## Campus map improvements

- Replaced the schematic campus with an interactive Leaflet/OpenStreetMap map
  centered on UIU using the user-provided campus link, not guessed buildings.
- Reports can save exact click/drag coordinates and a 10–500 m search radius.
  Owner-only location editing lets existing reports add or correct their pin.
  Both API routes validate coordinate ranges, paired coordinates and radius.
- Added item-page map previews, shareable selected-report links, walking
  directions, lost/found and returned filters, and clue-sharing through the
  public comments thread. Desktop/mobile layouts include map attribution.
- Optional geolocation sorts reports by approximate straight-line distance;
  explorer location remains in browser memory. This is not live tracking or an
  indoor campus routing system. Floors/rooms must be described in location notes.
- Removed the previous first-page-only map limitation by following report
  pagination. Missing coordinates remain explicitly unpinned; no location is
  inferred from old text descriptions. Map imagery requires internet access;
  manual coordinates and report details remain usable when imagery is unavailable.

## Ownership evidence and handover safety

- Claimants submit private identifying descriptions, partial serial details,
  or one validated image of an older photo/redacted receipt. Participant/staff
  authorization and `no-store` apply to image reads; public routes expose none
  of this evidence. New evidence invalidates previous evidence/staff reviews.
- Explicit poster evidence review precedes pickup approval. New approvals
  enter `APPROVED`, not `ACCEPTED`; the item stays pending and chat remains open.
  Only both distinct participant confirmations complete the return. Database
  locks serialize concurrent approvals/confirmations; one pickup is reserved.
- Electronics/jewellery and poster-marked valuables require campus-desk review
  and a staff attestation of an in-person student-ID check. Only approved
  administrators review; they cannot review their own claims or reports.
- Participant fraud reports freeze all handovers for the item and invalidate
  old handover confirmations. All disputes must be resolved, including those
  on withdrawn/declined claims; closing a claim cannot erase its dispute.
- Audit events retain scalar claim/item/account references, action, actor,
  timestamp and review/reason notes. There are no edit/delete HTTP endpoints.
  Database administrators can still alter records; no cryptographic tamper
  evidence, notification delivery or fraud-report throttling is implemented.
- Existing native enum databases require the supplied `APPROVED` migration.
  Historic completed claims are preserved without invented confirmations.
  The local H2 preview was backed up and upgraded without losing rows.
- `/help.html`, `/desk.html`, the local-only seed scripts and
  `docs/CLAIM_AND_COLLECTION_GUIDE.md` explain the collection workflow. ID checks are human
  attestations, not integration with UIU records. Evidence may still be forged.

## Validation

`PrivacyAndChatIntegrationTest` runs against H2 with open-in-view disabled and
tests the authorization and privacy behavior through the real HTTP controllers.
Frontend changes are checked with Node syntax validation and the Tailwind build.
A headless Chromium smoke check also completed the report form, both uploads,
incorrect/correct answers, two-participant message polling, draft preservation,
acceptance, private photo visibility and the account dashboard without browser
JavaScript errors.

The suite now includes 21 integration tests. Additional Chromium map checks
covered real tile loading, click/drag pins, coordinate/radius persistence,
owner-only edits, deep links, walking directions, opt-in geolocation, filters,
mobile layout, and pagination beyond 60 reports without invented pins. Saving
an editor immediately after changing coordinates no longer leaves a disposed
map's zoom animation running.

`frontend/tests/fraud-flow.cjs` also exercises private receipt-image submission,
human review, pending pickup, two-party completion, staff/ID-check gates,
fraud freezes, staff rejection, audit entries and mobile layout in independent
browser sessions. It passed without JavaScript errors. Integration tests also
cover simultaneous approvals and handover confirmations.
