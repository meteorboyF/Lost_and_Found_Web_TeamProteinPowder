## 1. Tech stack and how to run

| Layer | Technology |
|---|---|
| Frontend | Plain HTML pages, vanilla JavaScript (no framework), Tailwind CSS v4 |
| Maps | Leaflet (bundled in `static/leaflet/`) |
| Backend | Java 21, Spring Boot 4 (Spring Web MVC, Spring Data JPA, Bean Validation) |
| Database | MySQL 8 (Docker container `lostfound-mysql`, port 3307); H2 in-memory for tests |
| Auth | Server-side HTTP session (cookie), passwords hashed with PBKDF2 |
| Tests | JUnit 5 + Spring MockMvc (`src/test/java`) |

**Run locally:** `./run.sh`, then open <http://localhost:8080>.
It starts MySQL in Docker, rebuilds the CSS and starts Spring Boot.
Demo logins: `admin` / `admin123`, `student` / `student123`.

**Project layout**

```
src/main/resources/static/      ← FRONTEND (served as-is by Spring Boot)
    *.html                        one file per page
    js/*.js                       one script per page + shared scripts
    css/app.css                   generated by Tailwind (do not edit by hand)
frontend/src/input.css          ← Tailwind source: design tokens, components
frontend/genpages.py            ← generates the HTML pages (shared header/footer)

src/main/java/com/teamproteinpowder/lostfound/   ← BACKEND
    web/        controllers: HTTP endpoints (/api/...)
    web/dto/    request/response shapes (what JSON looks like)
    service/    business logic
    domain/     JPA entities = database tables
    repo/       Spring Data repositories = database queries
    config/     web security headers, schema checks
src/main/resources/application.properties        ← DB connection, upload dir, settings
src/main/resources/seed/*.json                   ← sample data loaded on first start
```

## 2. How a request travels through the app

Example: a student types in the search box on the Browse page.

```
browse.html ──loads──► js/browse.js
   │  load()  builds the query string
   ▼
LF.api.get('/api/items?q=wallet')          js/app.js  request()  (fetch wrapper)
   │  HTTP GET, session cookie attached
   ▼
WebConfig interceptor                       config/WebConfig.java  (security headers,
   │                                         blocks cross-site POST/PUT/DELETE)
   ▼
ItemController.list()                       web/ItemController.java   validates filters
   ▼
ItemService.search()                        service/ItemService.java  page size, escaping
   ▼
ItemRepository.search()                     repo/ItemRepository.java  JPQL query
   ▼
MySQL table `items`
   ▲
   └── rows → Item entities → ItemResponse DTO → JSON → browse.js renders cards with LF.itemCard (ui.js)
```

Every page works the same way: **HTML page → its JS file → `LF.api` (app.js) →
Controller → Service → Repository → MySQL**, and back as JSON.

**Errors** from anywhere in the backend are turned into one JSON shape
`{status, error, message}` by `web/ApiExceptionHandler.java`; `app.js` turns that
into an `ApiError`, and pages show `err.message` in a toast or under the form.

## 3. The full lost-and-found flow

```
 ① Register ─► ② Admin approves ─► ③ Post item ─► ④ Smart matches
                                                       │
     ⑩ Resolved ◄─ ⑨ Both confirm ◄─ ⑧ Poster ◄─ ⑦ Chat ◄─ ⑥ Poster ◄─ ⑤ Someone
        (Reunions)    handover        approves             reviews     claims it
                                                           proof       (secret answer)
```

| Step | What the user does | Page / JS | API | Backend |
|---|---|---|---|---|
| ① Register | Fills username, student ID, email, password | `login.html` (Register tab) | `POST /api/auth/register` | `AuthController.register` → user saved as **PENDING** |
| ② Approve | Admin opens Student Approvals, clicks **Approve** | `admin.html` / `admin.js` | `POST /api/admin/users/{id}/approve` | `AdminController.approveUser` → **APPROVED** |
| Sign in | Student signs in | `login.html` | `POST /api/auth/login` | `AuthController.login` → session created |
| ③ Post | Chooses Lost/Found, category, title, description, location (map pin), photo, **secret question + answer** | `report.html` / `report.js` | `POST /api/items` (multipart) | `ItemController.create` → `ItemService.create`, `StorageService.store`, `QuestionService.configure` (answer hashed) |
| ④ Match | Right after posting, and as notifications, the app suggests likely matches on the opposite side | `report.js`, `item.js`, `alerts.js` | `GET /api/items/{ref}/matches` | `MatchService.findMatches` (scores category, words, place, colour, date) |
| Browse | Anyone searches and filters the board | `browse.html` / `browse.js`, `map.html` | `GET /api/items?…` | `ItemService.search` |
| Comment | Anyone can post a public clue ("saw one near the library") | `item.html` / `item.js` | `POST /api/items/{ref}/comments` | `CommentController.add` (rate-limited) |
| ⑤ Claim | Clicks **This is mine**, answers the secret question, describes proof, optional evidence photo | `item.js` claim dialog | `POST /api/items/{ref}/claims` | `ClaimService.create` → `QuestionService.verify` (5 wrong answers = 15 min lock) |
| ⑥ Review | Poster opens the claim, checks proof, clicks **Mark evidence reviewed** | `claim.html` / `claim.js` | `POST /api/claims/{ref}/verify` | `ClaimService.verifyProof` |
| ⑦ Chat | Poster and claimant message privately | `claim.js` | `POST /api/claims/{ref}/messages` | `ClaimService.reply` |
| ⑧ Approve | Poster clicks **Approve for pickup** | `claim.js` | `POST /api/claims/{ref}/accept` | `ClaimService.accept` → claim **APPROVED** |
| (Valuable items) | Campus staff check student ID in person and clear the claim | `desk.html` / `desk.js` | `POST /api/desk/claims/{ref}/review` | `ClaimService.deskReview` |
| (Dispute) | Either side reports fraud: all handovers on the item freeze | `safety.js` | `POST /api/claims/{ref}/flag` | `ClaimService.requestDesk(dispute=true)` |
| ⑨ Handover | After meeting, **both** click **Confirm actual handover** | `safety.js` (on claim page) | `POST /api/claims/{ref}/handover` | `ClaimService.confirmHandover` |
| ⑩ Resolved | When both confirmed: claim **ACCEPTED**, item **RESOLVED**, other claims closed, item appears on Reunions | `gallery.html` | `GET /api/items?status=RESOLVED` | `ClaimService.confirmHandover` |
| Alternative | Owner got it back another way → **Mark as resolved** | `item.js` | `POST /api/items/{ref}/close` | `ClaimService.closeByOwner` |

**Status values**

- Item: `OPEN` (no claims) → `PENDING` (someone claimed) → `RESOLVED` (returned). Goes back to `OPEN` if every claim is declined or withdrawn.
- Claim: `OPEN` → `APPROVED` (awaiting handover) → `ACCEPTED` (returned) · or `DECLINED` / `WITHDRAWN`.
- Account: `PENDING` → `APPROVED` or `REJECTED`. Role: `USER` or `ADMIN`.

## 7. Database

MySQL database `lostfound`. Tables are created and updated by Hibernate from
the entity classes in `domain/` (`spring.jpa.hibernate.ddl-auto=update` in
[application.properties](../src/main/resources/application.properties)).

| Table | Entity | Key columns | Relationships |
|---|---|---|---|
| `users` | [User.java](../src/main/java/com/teamproteinpowder/lostfound/domain/User.java) | `username`, `email` (unique), `student_id` (unique), `password_hash`, `salt`, `role` (USER/ADMIN), `approval_status`, `security_failures` | owns items, comments, claims |
| `items` | [Item.java](../src/main/java/com/teamproteinpowder/lostfound/domain/Item.java) | `reference` (LF-2026-XXXX, unique), `kind`, `status`, `category`, `title`, `description`, `location`, `latitude/longitude`, `photo_url`, `private_photo_name`, `security_question`, `security_answer_hash/salt`, `desk_review_required`, `handover_frozen` | `user_id → users` |
| `comments` | [Comment.java](../src/main/java/com/teamproteinpowder/lostfound/domain/Comment.java) | `author_name`, `body`, `hidden` | `item_id → items`, `user_id → users` (null for guests) |
| `claims` | [Claim.java](../src/main/java/com/teamproteinpowder/lostfound/domain/Claim.java) | `reference` (CL-2026-XXXX), `status`, `proof`, `chat_unlocked`, `evidence_photo_name`, `evidence_reviewed_at`, `desk_review_status`, `poster_handover_at`, `claimant_handover_at`, `disputed` | `item_id → items`, `user_id → users` |
| `claim_messages` | [ClaimMessage.java](../src/main/java/com/teamproteinpowder/lostfound/domain/ClaimMessage.java) | `author` (POSTER/CLAIMANT/SYSTEM), `author_name`, `body` | `claim_id → claims` |
| `claim_audit` | [ClaimAudit.java](../src/main/java/com/teamproteinpowder/lostfound/domain/ClaimAudit.java) | `claim_reference`, `item_reference`, `action`, `actor_name`, `note` | none: stores references, so history survives deletions |

**ERD (simplified)**

```
users 1───* items 1───* claims 1───* claim_messages
  │           │            │
  │           └──* comments│
  └───────────────*────────┘ (claims.user_id = claimant)
claim_audit  (references only: claim_reference, item_reference)
```

**Enums** (stored as text): `ItemKind` LOST/FOUND · `ItemStatus` OPEN/PENDING/RESOLVED ·
`ClaimStatus` OPEN/APPROVED/ACCEPTED/DECLINED/WITHDRAWN · `Role` USER/ADMIN ·
`ApprovalStatus` PENDING/APPROVED/REJECTED · `Category` ELECTRONICS, ID_CARDS, KEYS, BAGS, CLOTHING, BOOKS, JEWELLERY, OTHER.

`lostfound`, password `lostfound`, schema `lostfound`. ERD: *Database → Reverse Engineer*.

**Possible questions**

1. **Where is the frontend code for the Post-an-item page?** `report.html` for the markup, `js/report.js` for behaviour; the map pin picker comes from `js/maps.js` (`picker`, [#L57](../src/main/resources/static/js/maps.js#L57)).
2. **When "Post item" is clicked, which API is called?** `POST /api/items` as `multipart/form-data`. Open [report.js#L191](../src/main/resources/static/js/report.js#L191) (`submit`) and [#L243](../src/main/resources/static/js/report.js#L243) (`fetch`). The JSON goes in an `item` part and photos in `photo` / `privatePhoto`. Backend: `ItemController.create`.
3. **Why `fetch` directly there, not `LF.api.post`?** Because it sends `FormData` (files). `LF.api` sends JSON.
4. **What happens when the Sign In button is clicked?** [login.html#L198](../src/main/resources/static/login.html#L198) → `LF.auth.login` [app.js#L430](../src/main/resources/static/js/app.js#L430) → `POST /api/auth/login`. On success it redirects to the `?redirect=` page (only same-site URLs are allowed, so the link can't send people to another website).

7. **Which API loads the comments, and which posts one?** `GET` [item.js#L297](../src/main/resources/static/js/item.js#L297) and `POST` [item.js#L321](../src/main/resources/static/js/item.js#L321) on `/api/items/{ref}/comments`.

10. **How do you stop XSS (someone posting `<script>` as a title)?** Every user value goes through `LF.escapeHtml` (`e()`) before it is put into HTML ([app.js#L474](../src/main/resources/static/js/app.js#L474)).
11. **How does the 3D hero work?** CSS 3D transforms on floating item icons in `index.html` ([#L127](../src/main/resources/static/index.html#L127)); `initHeroTilt` ([home.js#L102](../src/main/resources/static/js/home.js#L102)) tilts the stage toward the mouse and respects reduced-motion settings.
12. **How is dark mode done?** Colours are CSS variables in `frontend/src/input.css`; `app.js` sets `data-theme` on `<html>` and remembers the choice ([#L18](../src/main/resources/static/js/app.js#L18)-[L55](../src/main/resources/static/js/app.js#L55)).
13. **How do you build the CSS?** `cd frontend && npm run build` (Tailwind CLI: `src/input.css` → `static/css/app.css`). `run.sh` does it automatically.
14. **How are server validation errors shown on the form?** The API returns `{fields: {title: "…"}}`; `showErrors` in report.js ([#L92](../src/main/resources/static/js/report.js#L92)) puts each message under its field.

**How to explain your part in one minute:** "I own accounts and security.
Registration creates a PENDING user and an admin must approve it. Login checks
the PBKDF2 password hash and stores the user ID in the server session; every
later request reads it back through `CurrentUser`, which loads the user fresh
from the database, so approval or role changes apply immediately. Logins are
throttled against guessing, signups and comments are rate limited. I also
built the comments API and the admin moderation API."

**Possible questions**

1. **What does `POST /api/auth/login` do, step by step?** ([AuthController#L109](../src/main/java/com/teamproteinpowder/lostfound/web/AuthController.java#L109)) Check the throttle → find the user by email or username → verify the password (a dummy hash is checked when the user doesn't exist, so timing doesn't reveal which accounts exist) → on failure record it and return 401 → refuse PENDING/REJECTED with 403 → create a new session (new session ID) and store the user ID.
2. **How are passwords stored?** Never in plain text: a random 16-byte salt plus PBKDF2-HMAC-SHA256 with 65,536 iterations ([PasswordService#L27](../src/main/java/com/teamproteinpowder/lostfound/service/PasswordService.java#L27)). Columns `salt` and `password_hash`.
3. **What happens after 5 wrong passwords?** `LoginThrottle` returns 429 for 15 minutes for that account, even if the right password is then typed; there's also a limit of 30 per IP.
4. **How does the backend know who is calling?** The session cookie. `CurrentUser.from` ([#L28](../src/main/java/com/teamproteinpowder/lostfound/service/CurrentUser.java#L28)) reads `SESSION_USER_ID` and loads the user from the DB, accepting only approved accounts. `require` throws 401 otherwise.
5. **How does admin approval work?** `register` saves `approvalStatus = PENDING`. Admin calls `POST /api/admin/users/{id}/approve` ([AdminController#L261](../src/main/java/com/teamproteinpowder/lostfound/web/AdminController.java#L261)) → `APPROVED`. Login refuses PENDING/REJECTED.
6. **How is the admin role checked?** `requireKeyOrAdmin` in AdminController: the current user must have `role == ADMIN` (and be approved). Desk endpoints check the same.
7. **What does `POST /api/admin/users/{id}/role` do?** Changes USER↔ADMIN. Only approved accounts can be promoted; an admin can't demote themselves; the last active admin can't be removed (all admin rows are locked during the check).
8. **How do you prevent duplicate accounts?** Unique indexes on `email`, `username`, `student_id`. Student IDs are upper-cased first. If two signups race, the database rejects one and `ApiExceptionHandler` returns 409 "An account with this student email already exists".
9. **What does the comments API do?** `GET` lists visible comments; `POST` saves one, using the signed-in user's real name if logged in, else the typed guest name. Each comment has `verified` (true only for approved accounts) so a guest calling themselves "admin" shows a Guest badge.
10. **What is CSRF and how did you stop it?** Another website making the user's browser send a POST with their cookie. `WebConfig` rejects any non-GET `/api/**` request whose `Origin` isn't our own site.
11. **Why rate limit comments and signups?** Stops spam floods and stops using signup to test which emails are registered. Reading comments is never limited.
12. **What happens when an admin deletes a post?** `removeItem` ([#L168](../src/main/java/com/teamproteinpowder/lostfound/web/AdminController.java#L168)) deletes its comments and claims first (foreign keys), then the item, then its photo files after the transaction commits.
13. **What's in the `users` table?** id, username, email, student_id, student_email, password_hash, salt, role, approval_status, security_failures, security_window_started, created_at.
14. **How does the error JSON get its shape?** `ApiExceptionHandler` catches exceptions (validation, `ResponseStatusException`, DB conflicts) and returns `{status, error, message, fields}`; it never leaks SQL.

**How to explain your part in one minute:** "I own items and claims. Posting
goes through `ItemController.create`: photos are validated and saved with
random names, the secret answer is hashed, and the item gets a reference like
LF-2026-K7Q3. Searching is one JPQL query where every filter is optional. Matching
scores each opposite-side item on category, shared words, place, colour and
date. Claims are a state machine in `ClaimService`: open → approved → accepted
only after both people confirm the handover, with row locks so two people
can't approve at the same time."

**Possible questions**

1. **What does `POST /api/items` do?** ([ItemController#L105](../src/main/java/com/teamproteinpowder/lostfound/web/ItemController.java#L105)) Requires login → validates the JSON part (`ItemRequest` rules) → stores the photos (`StorageService`) → `ItemService.create` sets status OPEN, a unique reference, owner = current user, and hashes the secret answer → saves → returns `201` with the item. If saving fails, the uploaded files are deleted.
2. **How does search work in the database?** `ItemRepository.search` is one JPQL query: `(:kind IS NULL OR i.kind = :kind) AND …` plus a case-insensitive `LIKE` over title, description, location, colour. `%` and `_` in the search text are escaped so they match literally. Page size is capped at 60.
3. **How does matching decide two items match?** [MatchService#L97](../src/main/java/com/teamproteinpowder/lostfound/service/MatchService.java#L97): same category +0.30, shared meaningful words up to +0.30, same place up to +0.20, same colour +0.12, close dates up to +0.08. Score ≥ 0.35 is shown, with the reasons ("Both are electronics").
4. **How is the secret answer protected?** Normalised (lower-case, trimmed) and hashed with a salt like a password ([QuestionService#L39](../src/main/java/com/teamproteinpowder/lostfound/service/QuestionService.java#L39)). Checking ([#L52](../src/main/java/com/teamproteinpowder/lostfound/service/QuestionService.java#L52)) allows 5 wrong answers per user per 15 minutes; failures are saved in a separate transaction so they count even when the claim is rejected.
5. **What happens when someone clicks "This is mine"?** `POST /api/items/{ref}/claims` → `ClaimService.create` ([#L55](../src/main/java/com/teamproteinpowder/lostfound/service/ClaimService.java#L55)): lock the item row, refuse if resolved, if it's your own post, or if you already have an open claim → check the secret answer → save the claim (CL-2026-XXXX), the proof as the first message and an audit entry → item becomes PENDING.
6. **What does `/accept` check?** ([#L164](../src/main/java/com/teamproteinpowder/lostfound/service/ClaimService.java#L164)) Caller owns the item; chat is unlocked; claim is OPEN; evidence was reviewed; no dispute freeze or pending desk review; no other claim already approved.
7. **Why two handover confirmations?** So nobody can mark an item returned alone. `confirmHandover` ([#L185](../src/main/java/com/teamproteinpowder/lostfound/service/ClaimService.java#L185)) records each side; when both exist → claim ACCEPTED, item RESOLVED, all other claims DECLINED with a message.
8. **What is the campus desk for?** Valuable items (`deskReviewRequired`) or disputes need staff to check student ID in person. `deskReview` ([#L438](../src/main/java/com/teamproteinpowder/lostfound/service/ClaimService.java#L438)) clears or rejects; staff can't review their own claim.
9. **How do you stop two people approving at the same moment?** `items.lockByReference` uses `PESSIMISTIC_WRITE` (SELECT … FOR UPDATE), so claim actions on one item run one at a time.
10. **How are uploads made safe?** Max 5 MB; JPEG/PNG/WebP/GIF only; the real file type is detected from its bytes, not the name; ≤ 20 megapixels; saved under a random UUID name; GPS/EXIF metadata removed; served with `nosniff`.
11. **Who can see the private photo?** The owner, an admin, or the claimant whose handover was completed ([PhotoController#L34](../src/main/java/com/teamproteinpowder/lostfound/web/PhotoController.java#L34)).
12. **What is `claim_audit` and why no foreign key?** A permanent log of every claim action (who, what, when). It stores references instead of foreign keys so the history survives if an item is removed.
13. **How does the app connect to MySQL?** `application.properties`: `jdbc:mysql://127.0.0.1:3307/lostfound`, user/password `lostfound` (override with `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`). `run.sh` starts the Docker container. Hibernate creates/updates tables from the entities.
14. **What does "Mark as resolved" do on the backend?** `closeByOwner` ([#L269](../src/main/java/com/teamproteinpowder/lostfound/service/ClaimService.java#L269)): owner only; refused if already resolved, frozen by a dispute, or a claim is approved for pickup; sets RESOLVED and declines open claims with a message.

## 9. Questions anyone may be asked

| Question | Short answer |
|---|---|
| What is the architecture? | Client–server. Static HTML/JS frontend calls a REST JSON API; Spring Boot backend in layers (Controller → Service → Repository); MySQL via JPA/Hibernate. |
| What is a REST API here? | URLs that represent things (`/api/items`, `/api/claims/{ref}`) and HTTP methods for actions: GET reads, POST creates/acts, PUT updates, DELETE removes. Responses are JSON. |
| What is a DTO? | A class describing the JSON in or out (e.g. `ItemRequest`, `ItemResponse`). It keeps database entities private and hides secrets like password hashes. |
| What is a Repository? | A Spring Data interface; Spring generates the SQL from method names (`findByReference`) or from `@Query`. |
| What do `@Transactional` and `@Valid` do? | `@Transactional`: all DB changes in the method commit together or roll back together. `@Valid`: checks annotations like `@NotBlank`, `@Size` and returns 400 with field messages. |
| How do frontend and backend talk? | `fetch` (wrapped by `LF.api` in `app.js`) sends JSON with the session cookie; the backend replies with JSON. |
| How is login state kept? | A server-side HTTP session; the browser holds only a session cookie. |
| Where is the database configured? | `src/main/resources/application.properties`. |
| How do I run the tests? | `./mvnw test`: 76 integration and unit tests using an in-memory H2 database. |
| Who can do what? | Guests: browse, search, comment. Approved students: post, claim, chat, confirm handover. Admins: everything plus moderation, approvals, roles, campus desk. |
